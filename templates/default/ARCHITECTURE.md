## Repository Boundaries (顶层资产与仓库边界)

<!-- harness:placeholder
用途:
严格定义仓库顶层目录的资产属性、归属职责与隔离原则，防止跨工程代码污染与混乱。

包含内容:
- 顶层工程目录的职责映射
- 根目录的定位与纯粹性治理原则
- 新增顶级目录的准入条件

格式示例:
```text
repo-root/
├─ AGENTS.md             # 全仓 Agent 行为总入口与操作不变量
├─ ARCHITECTURE.md       # 系统全局架构拓扑、模块依赖与跨端契约
├─ docs/                 # 跨领域端侧工程规范 (docs/FRONTEND.md, docs/BACKEND.md)
├─ openspec/             # 唯一行为规格 (specs/) 与进行中的行为变更生命周期 (changes/)
├─ database/             # 数据库规范化 DDL、迁移脚本与受控基线测试数据
├─ frontend/             # 独立的前端工程 (Vite + React，拥有独立 package.json 与构建工具)
└─ backend/              # 独立的后端工程 (Java + Spring Boot，拥有独立构建脚本与测试)
```

边界准则:
- 根目录职责收敛: 根目录专注承载全仓治理文件、跨端规约与公共规格；子工程的依赖配置、源码及产物严格收敛于各自工程根目录。
- 前后端物理隔离: 前端与后端工程分别作为独立应用构建，跨端通信完全基于版本化网络契约。
- 数据库脚本托管: 数据库脚本统一收敛于 `database/`，由后端在运行时负责迁移执行，生成物保持自动化版本化管理。
- 资产准入原则: 仅为当前已真实落地的技术或能力建立顶层资产目录。

约束:
- 仅列出仓库中真实存在的顶层目录。
- 阐明设立各边界的架构意图，而非机械罗列文件树。
-->


## Dependency Flow & Architecture Invariants (单向依赖流向与架构铁律)

<!-- harness:placeholder
用途:
严格确立模块、层级与领域之间的单向依赖流向，制定全系统必须永久保持的确定性设计纪律。

包含内容:
- 全局单向依赖流向链条 (Unidirectional Dependency Rule)
- 跨业务特性隔离与提升原则 (Feature Isolation & Promotion)
- 领域逻辑纯粹性与展示层解耦
- 架构级不变量清单
- 端内垂直依赖职责归属 (下沉至 docs/FRONTEND.md 与 docs/BACKEND.md)

格式示例:
全局单向依赖流向链条:
`基础共享层 (shared / lib) → 业务领域特性层 (features) → 顶层应用外壳 (app / shell)`

端内垂直依赖职责归属 (单一事实来源):
- 前端内部模块结构、组件层级与状态归属以 `docs/FRONTEND.md` 为唯一权威来源。
- 后端业务能力垂直分包、四层架构职责与持久层封装以 `docs/BACKEND.md` 为唯一权威来源。
- 本节聚焦系统级跨领域依赖流向，端内微观分层由端侧工程文档独立承载。

架构级不变量清单:
1. 严格单向流动: 依赖方向始终自顶向下 (上层依赖下层)；底层共享库保持通用与自包含，仅通过抽象接口与上层协作。
2. 特性解耦与晋升: `src/features/` 下各业务领域保持平级自治；跨特性共享逻辑或类型统一晋升至 `shared/` 共享层。
3. 领域逻辑纯粹性: 核心业务规则与数据校验保持无副作用，独立于具体 UI 视图组件与外部网络传输框架。
4. 外部系统适配隔离: 访问第三方外部 API、大模型或非受控服务时，统一通过显式定义的防腐层 (Adapter / Client) 适配，业务层仅面向内部统一领域模型通信。
5. 自动化产物受控管理: 代码生成器、数据库快照或编译工具输出内容，统一由源定义文件重新生成并保持版本同步。

约束:
- 记录能够被 Linter、架构测试 (ArchUnit) 或代码审查机械验证的确定性规则。
- 使用明确、可判定的工程准则界定边界。
-->


## Cross-Boundary Contracts (跨端通信契约与协议规范)

<!-- harness:placeholder
用途:
定义前端与后端之间、或不同服务边界之间通信的统一标准、数据信封、会话透传与错误传播规范。

包含内容:
- API 通信协议与数据信封 (Response Envelope) 规范
- 统一认证、会话与多租户上下文的 Header 透传规则
- 错误码、业务异常与 HTTP 状态码的映射原则
- 前后端 DTO 与数据库实体的隔离要求

格式示例:
统一响应信封规范:
```json
{
  "code": 200,            // 业务状态码: 200 成功，非 200 为具体业务错误
  "data": { ... },        // 业务负载数据 (成功时返回)
  "message": "success",   // 面向用户的友好提示或错误摘要
  "traceId": "req-xxx"    // 全链路排查追踪 ID
}
```

上下文透传 Header 约定:
- `Authorization: Bearer <token>`: 传递当前用户会话凭证。
- `X-Tenant-Id: <tenant_id>`: 明确当前操作的活跃租户/工作空间上下文（由网关或受控前端注入，后端严格鉴权校验合法性）。

错误与异常传播原则:
- 网络传输层状态 (401 未登录, 403 越权, 404 不存在, 500 熔断) 与业务逻辑失败严格分离。
- 服务端所有未捕获异常统一由全局处理器转换为安全错误信封与用户友好提示；内部堆栈与 SQL 细节收敛于服务端安全日志。

契约隔离原则:
- 前端以版本化 API/DTO 契约为唯一交互标准，保持跨端契约显式解耦。

约束:
- 保持跨端协议层面的通用契约，详细业务接口入参下沉至接口文档。
-->


## Shared Data Architecture (全局数据模型与多租户隔离原则)

<!-- harness:placeholder
用途:
定义系统核心数据实体在跨端场景下的归属关系、多租户隔离底线与数据字典管理机制。

包含内容:
- 核心业务实体的权威归属
- 多租户与工作空间数据隔离准则
- 数据库表结构快照与数据字典治理
- 数据软删除与审计字段规范

格式示例:
多租户隔离准则:
- 数据隔离边界: 核心业务表统一包含 `tenant_id` (或 `workspace_id`) 字段；后端在数据持久层（如 MyBatis-Plus 拦截器）统一自动注入租户过滤条件，确保所有数据读写在受限租户作用域内执行。
- 租户上下文权威注入: 数据操作作用域由经过服务端验签的当前会话上下文决定，以验签凭证中的租户身份为唯一依据。

数据字典与实体快照:
- 权威数据字典位于 `docs/generated/data-dictionary.md`，由自动化工具从数据库结构或 DDL 逆向生成，作为只读参考物，源定义变更时由工具刷新。
- 公共审计字段标准: 核心表统一维护 `id`, `tenant_id`, `created_at`, `updated_at`, `created_by`, `deleted` 字段，严格执行逻辑删除与时间戳更新。

约束:
- 聚焦全局性、跨领域的数据架构准则，具体的表 DDL 脚本归属 `database/`。
-->


## Architectural Decisions & Evolution (核心架构决策与演进指引)

<!-- harness:placeholder
用途:
记录塑造当前系统的关键架构决策记录 (ADR)，并提供系统面向未来演进的健康边界与触发条件。

包含内容:
- 关键架构决策记录 (采用的架构模式、技术选型动因与权衡取舍)
- 架构变更的治理流程 (何时必须更新规格与架构文档)
- 系统的稳定扩展点与演进防腐策略

格式示例:
### 核心架构决策记录 (ADR 摘要)
1. 决策: 前后端独立工程物理隔离 (Decoupled Monorepo)
   - 动因: 前端基于 Vite 构建 SPA，后端基于 Maven 管理 Java，工具链独立且便于单独打包部署。
   - 权衡: 前后端通过明确的 REST/DTO 契约保障跨端一致性。
2. 决策: 后端业务能力按领域纵向分包 (Capability-based Packaging)
   - 动因: 摒弃全仓大一统的 `controller/service/dao` 模式，将同一业务领域的高内聚代码聚合在同一个根包下，方便后续平滑拆分服务。

架构演进与治理门禁:
- 涉及单向依赖流向调整、新增顶层资产目录或引入新外部中间件的改动，首先更新本文档并同步评审。
- 可观察的外部行为、API 格式或数据模型发生变更时，通过 `openspec/changes/` 发起变更提案并审核。
- 内部技术重构严格维护既定单向依赖流向与分层契约。

约束:
- 仅记录真正具有深远影响的架构决策，避免记录局部编码技巧。
- 保持演进指引立足已落地现状，保持客观与可执行。
-->
